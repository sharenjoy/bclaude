# Data Insight Orchestrator

## 概述

這是一個**完整的數據分析 skill**，包含：
- 分析流程編排（Phase 1-6）
- 分析方法論（假設驅動、So What 追問）
- 認知偏差檢驗庫
- 數據敘事框架

---

## 觸發條件

以下情況自動激活此 skill：
- 用戶上傳數據文件（.xlsx, .xls, .pdf, .docx, .csv, .txt）
- 用戶使用 `/analyze-data` 命令
- 用戶表達"分析數據"、"數據洞察"、"幫我分析"等意圖

---

## 執行流程

```
Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6
文件識別   詢問側重點  數據分析   圖表生成   頁面構建    交付
```

## Phase 2: 了解分析側重點

**必須在分析前完成此步驟**

向用戶詢問：

```
在開始分析之前，請告訴我：

1. 核心問題：你最想通過這些數據回答什麼問題？
   （例如：銷售趨勢、用戶行為、成本構成...）

2. 關注指標：有特別關注的指標或維度嗎？
   （例如：增長率、轉化率、某個時間段...）

3. 用途場景：這份分析的用途是什麼？
   □ 內部匯報（簡潔專業）
   □ 公開發布（視覺吸引）
   □ 決策支持（數據詳盡）

4. 其他要求：還有什麼特別需要注意的嗎？
   （可選，如：需要對比競品、關注異常值...）
```

**等待用戶回覆後再繼續下一階段**

## Phase 3: 數據分析

### 3.1 假設驅動分析（核心方法）

**不是"看看數據說什麼"，而是"用數據驗證假設、驅動決策"**

執行步驟：

1. **明確核心問題**
   - 問題重構：`"分析銷售數據"` → `"找到銷售增長的機會點"`
   - 確認：分析結果會影響什麼決策？

2. **構建假設樹**
   ```
   核心問題：為什麼 Q3 銷售下滑？
   │
   ├─ 假設1：需求端問題（市場萎縮/競品搶佔/需求轉移）
   ├─ 假設2：供給端問題（產品力/定價/供應鏈）
   └─ 假設3：渠道端問題（流量/經銷商/營銷效率）
   ```

3. **驗證假設**：按優先級逐個用數據驗證

4. **So What 追問**（每個發現至少追問3層）
   ```
   數據現象 → So What? → 業務含義 → So What? → 行動建議 → So What? → 預期影響
   ```

### 3.2 應用基礎框架

- **MECE**：相互獨立，完全窮盡
- **金字塔原理**：結論先行，以上統下
- **5W1H**：What/Why/Who/When/Where/How
- **對比分析**：時間對比/空間對比/標杆對比/目標對比

### 3.3 偏差檢驗（必須）

每個結論都要檢驗：

**統計陷阱**：
- [ ] 辛普森悖論：分組後結論是否仍成立？
- [ ] 倖存者偏差：有沒有看不到的數據？
- [ ] 回歸均值：極端值是否會自然回歸？

**因果檢驗**：
- [ ] 相關≠因果：是否把相關當因果？
- [ ] 反向因果：因果方向是否正確？
- [ ] 遺漏變量：是否有隱藏的混淆變量？

**心理偏誤**：
- [ ] 確認偏誤：是否在找支持預設的證據？
- [ ] 是否有反面證據被忽略？

### 3.4 核心準則檢查

- [ ] **因果推演**：每個結論是相關性還是因果性？鏈條是否完整？
- [ ] **可落地性**：用戶看完能做什麼？能在下週一開始執行嗎？
- [ ] **執行計劃**：短期如何破局？中長期如何積累複利？
- [ ] **反常識驗證**：如果結論反直覺，證據鏈是否足夠堅實？

### 3.5 提煉核心結論

- 交叉關聯多份文件的數據
- 提取 **3-7 個核心結論**
- 每個結論必須：有數據支撐 + 指向行動 + 可量化預期

# Part B: 核心分析準則

## 準則1：相關性 ≠ 因果性

**原則**：數據只能告訴我們"什麼在一起發生"，不能直接告訴我們"什麼導致了什麼"。

**推演方法**：
- 時間順序檢驗：原因必須發生在結果之前
- 排除第三變量：是否存在同時影響兩者的隱藏變量？
- 反向因果檢驗：是A導致B，還是B導致A？
- 機制合理性：因果鏈條是否符合常識？

**示例**：
```
錯誤：付費用戶生成圖片少 → 所以我們應該限制用戶生成圖片
正確：付費用戶生成圖片少，但修改次數多、使用時長長
     → 說明他們是"質量追求者"而非"數量追求者"
     → 因果推演：追求質量的用戶更願意為專業功能付費
     → 行動建議：服務這類用戶，強調"精修"價值主張
```

## 準則2：結論必須指向行動

**檢驗標準**：
- 具體性：能否在下週一就開始執行？
- 可衡量：執行後能否用數據驗證效果？
- 權責清晰：誰來負責執行？

**結論模板**：
```
[發現] + [原因分析] + [具體行動] + [預期效果]

示例：
發現：Android中端用戶轉化率(21.7%)是iPhone用戶(6.8%)的3倍
原因：這類用戶需要引導來明確需求
行動：① 保留風格選擇流程 ② 投放定向調整為Android中端
預期：付費轉化率提升15-20%
```

## 準則3：短期突破 + 中長期複利

| 階段 | 目標 | 思考重點 |
|------|------|----------|
| **短期（1-2週）** | 快速突破 | 最大痛點？什麼能立竿見影？ |
| **中期（1-2月）** | 建立飛輪 | 如何形成正向循環？ |
| **長期（3月+）** | 構建壁壘 | 什麼能產生複利？ |

**長期思考**：
- 這個動作做完後，是消耗掉了還是積累下來了？
- 一年後回看，這件事會不會越來越有價值？

## 準則4：反常識結論必須經得起推敲

當結論與常識相悖時，必須檢驗：
- [ ] 數據來源是否可靠？樣本量是否足夠？
- [ ] 是否存在選擇偏差或倖存者偏差？
- [ ] 能否找到支撐這個結論的第二數據源？
- [ ] 領域專家是否認可這個邏輯？

# Part C: 報告數據規範

## 寫作風格規範

**核心原則**：說人話，不要寫成營銷文案。

### 標題（title）
| 要求 | 好例子 | 壞例子 |
|-----|--------|--------|
| 直接說發現，不加修飾 | `Android中端轉化率是iPhone的3倍` | `被忽視的金礦——Android的驚人表現` |
| 用數字說話 | `抖音渠道ROI比信息流高2.4倍` | `抖音投放的隱藏價值` |
| 口語化，像同事聊天 | `付費用戶其實生成圖更少` | `付費用戶行為的反直覺真相` |
| 不用"驚人""顛覆""真相"等詞 | `老用戶復購貢獻了60%收入` | `老用戶的驚人貢獻` |

### 描述（description）
| 要求 | 好例子 | 壞例子 |
|-----|--------|--------|
| 解釋原因+給建議 | `完成風格選擇的用戶更明確需求，轉化更高。建議保留引導流程。` | `數據揭示了令人震驚的真相：風格選擇竟然是轉化的關鍵！` |
| 一句話說完，不鋪墊 | `朋友推薦渠道的Android用戶轉化最好，值得加大投放。` | `我們發現了一個被嚴重低估的機會點...` |
| 不用感歎號 | `這個渠道值得重點投入` | `這是被嚴重低估的金礦！` |

### 摘要（summary.overall）
| 要求 | 好例子 | 壞例子 |
|-----|--------|--------|
| 先說最重要的結論 | `Android中端用戶是核心付費群體，轉化率21.7%。抖音+朋友推薦是最優渠道組合。` | `我們深入分析了用戶數據，發現了多個重要洞察...` |
| 不要"我們發現""數據顯示" | `Q3銷售下滑主要因為華東區經銷商流失` | `通過深入分析，我們發現Q3銷售下滑的原因...` |

```json

  "meta": {
    "title": "報告標題（直接說分析了什麼）",

  },
  "summary": {
    "overall": "整體摘要：先說最重要的結論，再說次要的（100字以內）",
    "total_conclusions": 5,
    "high_importance_count": 2,
    "source_files": ["文件1.xlsx", "文件2.pdf"]
  },
  "conclusions": [
    {
      "id": 1,
      "title": "結論標題：數字+發現，不加修飾詞（15字以內）",
      "description": "解釋原因+行動建議，不鋪墊不感歎（80字以內）",
      "data_support": "關鍵數據，用分號分隔多條",
      "source_files": ["文件1.xlsx"],
      "importance": "high | medium | low",
      "chart_type": "bar | line | pie | scatter | area",
      "chart_data": { ... }
    }
  ]
}
```

## chart_data 格式

**柱狀圖 (bar)**：
```json
{
  "xKey": "name",
  "yKey": "value",
  "data": [{"name": "A", "value": 100}, {"name": "B", "value": 200}]
}
```

**折線圖 (line)**：
```json
{
  "xKey": "month",
  "series": ["actual", "target"],
  "data": [{"month": "Q1", "actual": 100, "target": 90}]
}
```

**餅圖 (pie)**：
```json
{
  "nameKey": "name",
  "valueKey": "value",
  "data": [{"name": "華東", "value": 42}, {"name": "華南", "value": 28}]
}
```

## 具體觸發條件

### 1. `hypothesis-driven-analysis.md`（假設驅動）
**何時讀取**：
- 用戶給的問題很模糊（如"幫我分析一下"）
- 需要構建假設樹
- 需要做 So What 追問但不確定怎麼追

### 2. `cognitive-biases.md`（認知偏差）
**何時讀取**：
- 發現的結論與常識相悖
- 數據呈現的趨勢很"完美"，需要懷疑
- 需要檢驗：辛普森悖論、倖存者偏差、相關≠因果
- 用戶質疑結論的可靠性

### 3. `driver-tree-analysis.md`（驅動因素樹）
**何時讀取**：
- 需要拆解"為什麼收入下降"
- 需要量化各因素的貢獻度
- 需要做敏感性分析（哪個槓桿影響最大）

### 4. `data-storytelling.md`（數據敘事）
**何時讀取**：
- 用戶說"要向老闆匯報"
- 需要寫執行摘要
- 需要 SCR/SCQA 敘事結構
- 需要針對不同受眾調整內容

### 5. `visualization-rules.md`（可視化規則）
**何時讀取**：
- 不確定該用柱狀圖還是折線圖
- 圖表設計有疑問

### 6. `general-frameworks.md`（通用分析框架）
**何時讀取**：
- 需要用 MECE 拆解問題
- 需要金字塔原理組織結論
- 需要 5W1H 全面覆蓋

### 7. `data-interpretation.md`（數據解讀）
**何時讀取**：
- 遇到異常值不知道怎麼處理
- 需要確定對比基準
